# Test Case Catalog

The single source of truth for **what the 40 automated tests actually verify**, in
business terms. Generated by reading every `test()` in `tests/smoke/` and
`tests/regression/` on 2026-08-31 — every row below corresponds to exactly one real,
currently-passing Playwright test. Nothing here is aspirational; scenarios that were
planned but never implemented are **not** listed as if they existed (see
`docs/test-strategy.md` for what was intentionally descoped, and §4 below for what's
genuinely missing).

> **Update (2026-08-31, later same day):** ASN-003 added after a coverage-gap review
> requested by the team — see §4 for the review's findings and why this was the one gap
> chosen to close first. Total is now 41 tests (was 40).

## Authentication setup vs. business tests

`tests/auth.setup.ts` runs 4 tests — one per role (Super Admin, Secretary, multi-division
Joint Secretary, Division User). These are **infrastructure, not business test cases**:
they log in once per role and save `storageState` so every other test can reuse the
session instead of logging in repeatedly. They are excluded from the 40 below and from
every count in this document. Their business counterparts — actually asserting that
sign-in redirects to the correct screen — are AUTH-001/002/003, which run as real,
independent test cases on top of (not instead of) the setup fixture.

**Total: 41 business test cases + 4 auth-setup fixtures = 45 entries in the HTML report.**

## 2. Test quality review (per this round's request)

Went back through all 40 tests asking: does this verify real business behavior, or is it
a UI/visibility check wearing a business-sounding name? Two findings, both addressed:

- **DASH-001's title claimed "clickable KPI cards" but the test never clicks anything** —
  it only checks the cards are visible. Renamed to
  `should display the Executive Dashboard KPI cards` so the title matches what's actually
  verified. The real "does clicking a KPI card navigate to the correctly-filtered list"
  behavior is **not yet tested anywhere** — see the gap list below (DASH-004).

- **TRF-001 and COL-001 are the two weakest tests in the suite, and they're weak for the
  same reason**: both only exercise the environment's current **zero/empty state**.
  TRF-001 asserts the Incoming/Sent tabs show correct empty-state copy — real UI-copy
  correctness, but no actual transfer ever happens. COL-001 compares a dashboard KPI to a
  tab count, but because the only Division account available currently has zero
  collaboration requests, it's really asserting `0 === 0` — technically a real
  assertion, but not exercising the counting logic for any value that would actually
  catch a miscount. **Neither was changed** (there is no non-mutating way to make them
  test more without live transfer/collaboration data, and inventing fake data was
  explicitly ruled out) — but this is exactly why Transfer lifecycle and Collaboration
  lifecycle are flagged as the top missing P0 workflows below, not just "nice to add."

No other tests were found to be shallow relative to their stated purpose. Smoke tests
(QST-001/002, ADM-001, ASN-001, CMP-001, ANS-001, AUTH-001-004, DASH-001) are
_deliberately_ shallow — that is the point of a smoke suite — and are not counted against
this review.

## 4. Coverage gaps

As of this review, the most important gaps — cross-referenced against what's actually
achievable with current test accounts — are: **Transfer, Collaboration, and any live
Draft→Submit→Complete action are all blocked by the same constraint** — none of the three
divisions we hold login credentials for (Export Promotion (Agriculture), Cash-I,
Establishment-I) currently has an active question, and the divisions that do
(Foreign Trade (NAFTA), Export Infrastructure, etc.) aren't among the provided test
accounts. This is a **test-data/credential dependency**, not a framework limitation.

**ASN-003 was added as the one exception**: a genuine, previously-untested business rule
(Pull Back Question is disabled once a division has started answering — the same
"can't undo after work starts" pattern as Bug Sheet DEF-013's Transfer-button defect) that
turned out to be fully testable read-only, cross-division, as Parliament — with no
division login and no shared-state mutation required. It was the one P0-adjacent gap that
didn't run into the credential constraint above.

Everything else in Transfer/Collaboration/Completion-action territory remains an open gap
pending either: (a) test accounts for a division that currently holds an active question,
or (b) a safe, repeatable way to get a fresh question into one of our three accessible
divisions without polluting the shared environment on every CI run.
